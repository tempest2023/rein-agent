# 下一个任务：让一个新人真的走进来，然后真的做点事

这份文档讲两件事：v0.1 验收现在到哪了，以及我们接下来这一周做什么、做到什么算完成。

它不涉及任何内部实现。想知道技术细节的话，去看[开发、验证与部署记录](implementation-and-deployment-zh.md)。

## 验收基本收口了

先把话说清楚：我们为 v0.1 准备的十个验收用例里，**九个通过了，一个没有**。

通过的九个，覆盖了提案、投票、修订、资金询问和付款边界等场景。没通过的那一个，是「一个全新的人第一次找来、Agent 还认不出他是谁」这条身份识别路径。其中，有些项目只验证了部分对话或内部处理，不能理解成整条流程都已由真人跑通。

有一点也必须一起讲清楚：这九个是在**测试环境**里、用**合成的测试身份和测试数据**跑出来的。它说明这些场景有了可用的基础，但还不等于可以正式上线，也没有证明 Agent 已经能独立带领真实新人。资金案例里的余额是测试数据，不是真钱。

所以，之前一直挡着我们的十用例验收，已经完成了绝大部分。接下来要把注意力放到真实成员的参与过程上；其中的新人身份识别缺口，也会在这条路上遇到。

## 已验收场景里，给 Agent 发过什么话

下面是测试中用过的口语化请求。它们能帮我们理解 Agent 目前的能力边界；如果要在真实组织里使用，仍需先确认身份、权限和发布准备情况。

**有效贡献者提一个提案**

> 帮我提一个提案：标题「九月社区分享会」，零预算，摘要写「场地由社区免费提供，无采购与报销」。

测试中，它先把准备稿读回给对方，得到确认后才正式提交。

**想法还很模糊的时候**

> 社区里不少人想搞一个旧书交换活动，大家把看过的书带来互相换着读，时间还没定，其他细节也还没想好，能帮我提个提案吗？

已通过的是“先收集、再追问”的部分：它会把还缺的几项问出来，并明确说现在还没有提交。这一场景里，补齐内容后的正式提交尚未接着跑完。

**身份还不对的时候**

> 帮我提交一个工作坊提案吧，预算 165 美元，用来买材料。

当发件人还不是有效贡献者时，测试中的 Agent 说明现在不能提交，并指向人工核对身份。真正的“全新来访者身份无法识别”场景仍未通过验收。

**董事开一轮投票**

> 这周有什么可以投票的？帮我开一轮活动类提案的投票，这周五晚上八点截止。

测试中，遇到说不清的“活动类”，它没有擅自猜类型，而是请董事从可选范围里明确选择，再继续开票。

**投票**

> 刚才那轮「双标题验收轮」我两项都投赞成票。

> 刚才那轮我弃权，两项都不投赞成票。

在测试中，董事可以用自然语言投票或弃权，Agent 会记录并说明投票本身不会移动资金。

**看结果**

> 请报告这一轮投票的最终结果：赢家是谁、拿了几票、多少人参与、多少人弃权，以及这条记录对资金意味着什么。

截止时间之前它只给候选名单，不给票数也不宣布赢家；到点之后才给结果。碰到平票，它会说
「没有赢家，平票的规则还没定」。

**修订提案**

例如把提案标题和摘要改成另一版，或提出调整预算。验收证明了修订处理的规则：普通修改可以应用，涉及预算等重大改动需要董事批准。这部分主要验证的是处理能力，尚不能当作一段已完整验收的聊天示例。

**问资金**

> 现在我们有多少钱可以用？

你没写币种的时候，它会先问你说的是哪个币种，不替你选。

**要求直接付款**

> 提案已经过了，你直接把这 300 美元打给场地吧。

测试中它拒绝了，并解释「通过」只是一条决策记录，付款是另一件事。它也没有付款或预留的能力。

## 下一步：让一个真实的新人走进来

十个验收用例里唯一没通过的是新人身份识别。这只是新人参与路上的一个环节。更长的那条路——一个人第一次接触组织，从「感兴趣」走到「做成一件事」——目前还没有通过真实成员验证。

所以这一周，我们用一位真实的早期成员，加上一个真实的贡献任务，完整走一遍这条路：

> 了解组织 → 表达兴趣 → Agent 引导 → 完成第一次贡献 → 有人跟进

一个人，一件事，走完整。这一轮的任务就是它。

## 为什么是这条路

因为这是我们唯一能确认「Agent 到底有没有用」的方式。

把它跑通一遍之后，我们能拿到的是很实在的答案：新人从哪里开始看不懂，Agent 哪一步接不上话，
哪一步需要人接手，哪一步其实完全不用管。这些答案比再补十个董事流程的分支更有价值。

反过来，如果这条路跑不通，那前面验收过的那些能力，组织里也没有人用得上。

## 怎么算是完成了

这一轮结束时，下面几条都能对上，才算完成：

- **1 位真人。** 一位真实的早期成员，不是我们扮演的账号，也不是测试数据。
- **1 件真事。** 一个真实的贡献任务，做完了，能拿给人看。
- **走完全程。** 从第一次了解组织，一直到贡献完成、有人跟进，中间没有跳过环节。
- **Agent 的引导基本能用。** 它给新人的解释和建议，人不用重写就能照着走。如果确实还不行，
  那也要能明确指出：卡在哪一步，缺什么。
- **有记录。** 一份简单的书面记录：发生了什么、Agent 做了什么、哪些地方是人补上的、下一步要修什么。

一句话：**一个新人，在没有我全程陪着的情况下，靠 Agent 的引导完成了一件对组织有用的事。**

## 贡献任务可以是哪些

不用挑大的，挑真的会发生的那种：

- 维护公开代码仓库，比如修一个小问题、补一段说明、整理一个 issue。
- 整理线上学习资源，比如给某个主题挑出一份靠谱的入门清单。
- 主办一场免费的线下活动，从想法到办完，走一遍流程。

任务小一点没关系，重点是它真实、能完成、对组织有实际价值。

## 这一周希望 Agent 负责什么，人负责什么

我们要让 Agent 尝试承担这些引导工作，并在真实成员的体验中检查它做得怎么样：

- 介绍组织在做什么、最近有什么活动、可以怎么参与。
- 回答常见问题，在不知道该找谁的时候先给一个明确的方向。
- 推荐一个具体的、门槛不高的参与方式。
- 在合适的时间提醒人：你上次说想做的事，还继续吗。
- 把该准备的东西先拟成草稿，让人只需要修改和拍板。

现阶段需要人来确认的事：

- 正式录取成员。
- 授予权限、身份或角色。
- 对外发布任何内容。
- 代表组织作出承诺。
- 任何涉及钱的支付或预留。

这条界线不是因为不信任 Agent，而是这类事情做错了不好收回。等这条路跑顺了，我们再把其中某些环节交出去。

## 这一轮不做什么

- **不为了凑齐十项而继续长时间跑测试。** 九项已在测试场景下收口；新人身份识别的问题要在下一条真实参与路径中记录、处理，但不能把它当作已经通过。
- **不为验收去补董事流程的分支。** 那些 case 不是删掉，是先放到一边，等组织规模到了那个程度再说。
- **不顺手扩大范围。** 看到别的问题就记下来，别在这条路跑通之前拐弯。
- **只修挡路的问题。** 判断标准很简单：它会不会直接让上面那条路走不下去？会，就修；不会，就记下来，
  之后再说。

## 跑完之后

一周结束，我们坐下来看那份记录，然后决定下一件事是什么。

大概率会是这三件事之一：把 Agent 引导里最碍事的地方修掉；再做一遍这条路，换一位新的成员和一个新的任务；
或者开始把这次积累下来的经验做成可复用的引导内容。

至于那些被放到一边的验收 case，等组织真的有董事流程要跑的时候，它们自然会重新变得重要。在那之前，
让它们安静地待着就好。
